# Khata - offline-first udhar and jama ledger (PWA + Cloudflare Worker)

A production-ready digital ledger for shopkeepers. Every entry is written to the device first
(IndexedDB), so the app keeps working with the network off. When connectivity returns, a
Cloudflare Worker receives the queued rows, stores them in D1, and texts the customer an SMS
alert.

- **Web app (PWA):** https://merry8989-uk.github.io/khata-pwa/app/
- **Android app (signed APK):** https://github.com/merry8989-uk/khata-pwa/releases/latest
- **Public page (feature reference):** https://merry8989-uk.github.io/khata-pwa/
- **Version:** 1.1.2 · package id `io.github.merry8989uk.khata`

## Requirements

- Node.js 20 or newer
- A Chromium/Chrome binary for the e2e test (the sandbox used `/usr/local/bin/chromium`;
  set `CHROME_PATH` if yours is elsewhere)
- Optional, for cloud sync: a Cloudflare account with `wrangler` available through `npx`
- Optional, for SMS: a Fast2SMS or Twilio account

## Run it locally

```bash
npm install
npm run build          # compiles Tailwind, assembles docs/app, writes version.json
npm run serve          # http://localhost:4173
```

`npm run serve` serves the built app from `docs/app`. Service workers need `localhost` or
HTTPS, which is why the built output is served rather than opening the file directly.

```bash
git init

```

Then in the repository: **Settings > Pages > Build and deployment > Source: GitHub Actions**.
(Only needed once per repository: the first `configure-pages` run can create the site itself
when the workflow token has the Pages permission, otherwise the settings page enables it.)

- `https://merry8989-uk.github.io/khata-pwa/` - the public page documenting every feature

Everything is served from a relative path, so it works from a project subpath without changes.

## Deploy the Worker (cloud sync + SMS)

```bash
# 1. Create the D1 database and the KV namespace for tokens
npx wrangler d1 create khata
npx wrangler kv namespace create AUTH

# 2. Paste the returned database_id and KV id into worker/wrangler.toml

# 3. Create the tables
npx wrangler d1 execute khata --config worker/wrangler.toml --remote --file worker/schema.sql

# 4. Deploy
npx wrangler deploy --config worker/wrangler.toml
```

Wrangler prints the Worker URL, e.g. `https://khata-api.<subdomain>.workers.dev`. Put it in
`khata.config.json` and rebuild - that is the entire client configuration:

```bash
# khata.config.json
{ "apiBase": "https://khata-api.<subdomain>.workers.dev" }

npm run build     # bakes API_BASE into docs/app/js/config.js and into the CSP connect-src
```

Nothing is pasted into the app. On first launch the app mints a 256-bit device key, and the
Worker keys its token store on the SHA-256 of that key, provisioning a shop the first time the
device writes. The status badge moves from "Local only" to "Online" and queued rows flush.

`SHOP_TOKEN` remains an optional secret for curl and support work: it maps to `SHOP_ID` and gives
that one shop full access.

Verify the server without the app:

```bash
curl https://khata-api.<subdomain>.workers.dev/api/health
# {"ok":true,"version":"1.0.0","checks":{"db":"ok","kv":"ok","sms":{"provider":"none","enabled":false}}}

# with the optional operator token
curl https://khata-api.<subdomain>.workers.dev/api/whoami \
  -H "authorization: Bearer $SHOP_TOKEN"
# {"ok":true,"shop_id":"default","counts":{"customers":0,"transactions":0},...}
```

### Customer SMS (free, from the phone's SIM)

SMS is sent by the Android app from its own SIM: no gateway, no per-message fee, no top-up, and
it works with the internet off. The message is the same template as before:

```
Dear Ramesh Kumar, Rs.5,000 Gave on 07 Nov 2026. Net Balance: Rs.3,750.- KhataApp
```

How it behaves:

- Sent after an entry is saved, once per entry. The entry is marked `sent` only when the radio
  reports the network accepted it; a failure is stored on the row and shown in the timeline
  rather than being passed off as delivered.
- The app asks for `SEND_SMS` on the first attempt. Without it nothing is sent and the entry is
  still saved.
- A daily cap of 90 messages (a normal Indian recharge pack allows about 100/day) is enforced in
  the shell, and Settings shows `N of 90 messages sent from this SIM`.
- Turning **SMS alerts on new entries** off stops it entirely.
- When the phone is doing the texting, the app sends `sms_alerts: false` to the Worker, so the
  server-side gateway can never double up.

This is for a shop's own customers, one message per entry. Bulk or promotional SMS in India needs
DLT registration and a registered sender; a personal SIM is not the channel for that.

### Optional: server-side SMS

The Worker still supports Fast2SMS and Twilio for anyone who wants messages to leave from a server
instead of a phone. It is off by default:

```toml
[vars]
SMS_PROVIDER = "fast2sms"   # or "twilio" or "none"
SMS_DAILY_CAP = "200"
ALLOWED_ORIGINS = "https://merry8989-uk.github.io"
```

```bash
npx wrangler secret put FAST2SMS_API_KEY --config worker/wrangler.toml
# or TWILIO_ACCOUNT_SID / TWILIO_AUTH_TOKEN / TWILIO_FROM
```

Every attempt is recorded in `sms_log` with status `queued` / `sent` / `failed` /
`skipped_cap`, a `UNIQUE(shop_id, transaction_id)` key that makes a send at-most-once, and a
daily cap. Retry failures with:

```bash
curl -X POST https://khata-api.<subdomain>.workers.dev/api/sms/retry \
  -H "authorization: Bearer $SHOP_TOKEN"
```

With `SMS_PROVIDER = "none"` the API responds `sms: {enabled: false, note: "sms_disabled"}`
and sends nothing.

## Rent mode

A tenant does not follow the calendar. Someone who moves in on the 20th rents "20th to 19th" and
usually pays on the 19th for the month that just finished, so rent is anchored on the move-in day.

- **Turn it on per customer**: rent toggle, monthly amount, the day they moved in, and whether the
  charge lands **at month end** (arrears, the default - charged the day before the next anniversary)
  or **in advance** (on the anniversary itself).
- **It accrues by itself.** Every pass adds the months that have come due: at launch, when the app
  returns to the foreground, and after a tenancy is edited. Turning the rent off stops it and keeps
  the history.
- **Charges are normal entries**, so balances, statements, search and sync need no special cases.
  They are labelled `RENT`, are never texted to the tenant, and still queue for the server.
- **Idempotent.** Each charge's id is derived from the customer and the month, so a reload, a second
  tab or a double run cannot charge a month twice.
- **Deleting a charge sticks.** The month is remembered in `rent.skipped`, otherwise the next pass
  would put it back.
- **The card** shows the rent, the move-in date, the day the month runs on, the next due date and how
  many months have accrued, plus a one-tap **Rent received** that prefills the payment at the rent
  amount.

Short months are clamped (a tenancy starting on the 31st charges on 28/29 February), a tenancy with
an end date stops charging after it, and changing the rent only affects months not yet charged.
What it deliberately does not do: deposits, electricity splits, agreements, notice periods, or
pro-rating a part month when someone leaves mid-month.

## How the offline queue works

1. A save writes the row to IndexedDB with `synced: false`.
2. `sync-core.js` collects every unsynced row (plus deletion tombstones) into one POST.
3. The Worker validates row by row and upserts with `ON CONFLICT DO NOTHING` on the
   client-generated UUID, so a replayed batch cannot duplicate anything.
4. The response lists accepted ids; the client marks exactly those as synced.
5. A row the server rejects is also marked synced (and logged) so one bad row cannot block the
   queue forever - the data stays on the device.

Triggers: the `online` event, Background Sync (`khata-sync`, runs even with no tab open), a
configurable interval, returning to the tab, and the "Sync now" button.

## Data model

| Table | Key | Notes |
| --- | --- | --- |
| `customers` | `(shop_id, id)` | `id` is a client UUID, `phone_number` is E.164 |
| `transactions` | `(shop_id, id)` | `type` is `GIVEN` or `GOT`, `amount_paise` is an integer > 0, `deleted` is soft |
| `sms_log` | `(shop_id, transaction_id)` unique | status, provider id, error, timestamps |
| `shops` | `id` | created on first sync |

Locally, `deletions` holds tombstones for rows the server may already know, `logs` holds
diagnostics (capped at 2000 entries), and `settings` holds every option.

## Accessibility and security notes

- Semantic HTML, one `h1` per view, labels tied to inputs, `role="switch"` toggles with
  `aria-checked`, a focus trap and Escape handling in every sheet, an `aria-live` toast region,
  visible focus rings, `prefers-reduced-motion` respected, and WCAG AA contrast.
- A strict Content-Security-Policy (`script-src 'self'`, `object-src 'none'`,
  `base-uri 'none'`) - no inline scripts, no CDN at runtime, no `eval`.
- User text is written through `textContent`; `innerHTML` is only used for the static icon set.
- The sync token is stored on the device in IndexedDB and never in the bundle.
- No analytics, no third-party requests at runtime.

## Android app (signed APK, auto-released)

`android/` is a thin shell around the same PWA: a full-screen WebView, a bridge that saves PDF
statements, JSON backups and log exports into Downloads (blob downloads never reach a WebView's
download listener), external links pushed out to the system, a native crash log, and an in-app
update that downloads the next APK and hands it to the installer. Everything else - the ledger,
Settings, Diagnostics, About - is the web app, unchanged.

- **Package id:** `io.github.merry8989uk.khata` (permanent; it never changes, which is what lets a
  new version install over the old one).
- **Signing:** one release keystore, generated once for this app and reused forever. The keystore
  and its passwords live in the repository's Actions secrets (`ANDROID_KEYSTORE_BASE64`,
  `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD`) and are decoded into
  the build only for the duration of a release job. They are never committed, and the release job
  refuses to build if the secret is missing rather than shipping an unsigned or debug-signed APK.
- **Automatic release:** pushing a tag like `v1.1.0` builds the web bundle and the signed APK,
  verifies the APK's signing certificate is the Khata key, and publishes both on the GitHub
  Release for that tag. The app then offers that release to installed copies by itself.

Build it yourself:

```bash
# debug build, no signing needed
npm run android:debug        # -> android/app/build/outputs/apk/debug/app-debug.apk

# release build (needs the keystore)
cd android
KEYSTORE_FILE=khata-release.p12 \
KEYSTORE_PASSWORD='…' KEY_ALIAS=khata-release KEY_PASSWORD='…' \
gradle :app:assembleRelease -PkhataVersionName=1.1.0 -PkhataVersionCode=10100
```

Release a new version:

```bash
npm version patch --no-git-tag-version   # bumps package.json
git commit -am "chore: release"
git tag v1.1.1 && git push origin main --tags
```

The workflow does the rest: lint, unit tests, build, sign, verify, publish.

## Known limitations

- A ledger belongs to the key its phone minted on first launch. A second phone starts a separate
  shop, and there is no linking, recovery or per-user role model yet.
- Concurrent edits of the same customer on two devices resolve last-write-wins.
- SMS requires your own gateway account and credit.
- Clearing browser site data deletes the ledger - use **Settings > Data and backup** first.
- The Android shell loads the hosted PWA, so the very first launch needs a connection; after that
  the service worker serves it offline. Web-side changes reach installed APKs without a new
  release; native changes need one.
- The APK is distributed through GitHub Releases, not the Play Store, so Android will ask the
  user to allow installing from this source once.
